对比

这一页不试图证明 brk 更好。它只做一件事：把 brk 和主流方案的差异摊开， 让你自己判断哪一套更适合手上的项目。
如果读完之后你选了别的方案，这一页也完成了它的工作。

//

对比是诚实的难点。brk 的体积优势、简洁模型是真实的； 但生态、工具链、社区支持上的差距也是真实的。

下面每一处"brk 更好"的结论，都会配上对应的代价。没有免费的午餐。

不是更小的 React

最容易被误解的一组。brk 和 React 的差别不在体积，而在组件执行模型——React 反复执行函数，brk 只执行一次。

渲染模型 hooks 取舍 ref vs ctx
brk vs Vue →

放弃响应式之后

Vue 的核心是响应式系统，brk 主动放弃它。换来的是更小的体积、更少的隐式依赖，以及需要自己管的更新。

响应式 SFC 心智模型

两种"微前端"

名字最像的一组，实际解决的场景却几乎不重叠。qiankun 解决"多团队、独立部署、强隔离"；brk 解决"同团队、同栈、页面组织"。

沙箱 隔离 适用场景

// 选别的
你认同「渲染一次」这个模型
你的组件在生命周期内不需要重渲染，更新逻辑你愿意自己写。
你希望组件自动响应状态
数据变了，DOM 就应该变——这是 React / Vue / Svelte 的强项。
你对页面体积敏感
希望页面产物里没有框架 runtime，加载即执行。
你希望开箱即用
组件库、路由、表单、状态、SSR——希望有一整套官方方案，而不是自己搭。
你在组织页面，而不是重写框架
项目需要的是"一套干净的多页结构"，而不是"另一套 UI 开发范式"。
你要做组件化 UI 系统
复杂交互、状态共享、动态表单、动画编排——这些场景 React / Vue 更成熟。
团队少、栈统一、想自己掌控
你愿意为精确控制多写几行代码，而不是被抽象层罩住。
多团队、异构栈、独立部署
需要沙箱、需要隔离、需要各自升级不互相影响——qiankun / Module Federation 更合适。
你想要一个骨架，不是框架
init.js 是源码，可以整体替换，改得动、看得穿。
你不想看到框架源码
希望框架是黑盒，稳定可靠、长期有人维护、有商业支持。
// 坦率地说

brk 不是大多数项目的正确选择

对绝大多数团队、绝大多数项目而言，React / Vue 是更安全的选择—— 生态、招聘、工具链、社区答案、长期维护，都是 brk 无法比拟的。

brk 面向的是一个很窄的场景：一个小团队，用同一套技术栈，需要一个干净的多页骨架， 并且愿意为"精确掌控"承担更多手工活。

如果你不属于这个场景，这一页的对比不是用来"说服你"的，而是用来"帮你快速排除"的。 排除得越快，你省下的时间越多。
