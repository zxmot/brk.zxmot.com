02

名字暂且叫 brk 吧，在没有正式发布前都可以斟酌，技术支持是 TypeScript；给你一个最简单的示例页面吧：

import {brk} from '@/brk';

const vino = () => {
    return(
        <div css='padding: 4px'>
            <brk.card>
	            <h1>Hello World</h1>
	            <div cls="bge" css="height: 1px; margin: 4px 0 8px"/>
            </brk.card>
        </div>
    );
}

export const page = {
	vino,
};

首先我魔改了 jsx 的标签，用 cls 表示 className，用 css 代替 style，用 clk 代替 onClick，因为这几个属性太频繁了，简短一点的表示更加优雅；其次我定义了页面结构，export const page = { vino } 这样就可以从其他页面异步加载这个页面了；对了你可能注意到 <brk.card></brk.card> 是一个内置且统一的卡片组件，也是因为太常用了。

收到。核心：cls / css / clk 三个简写、page.vino 页面契约、brk.card 内置组件。

三件事要弄清：JSX 怎么编译？css 落到哪个 DOM API？"微前端"体现在哪？

03

A. 我是用 esbuild 来做编译 jsx 的，转化为类似于 jsx("button", { cls: 'btn1', css: 'background: #369', clk: () => _exec("param") }, "一个按钮") 的形式。

B. 我会将 <div css='字符串value'/> 翻译成 div_element.setAttribute('style', css_value)。

C. 约定的 page.vino 是写死的，因为还可以有 export const page = { bare, card, vino } 也可以导出部分视图，为什么叫 vino 是为了和 view 相似，但必须区分，因为 view 是一个太范化而有歧义的名字。

D. 这是重点，接下来我会慢慢 brk 内部的技术细节，包含了许多强大的功能。

清楚了。esbuild 只做标准转换，jsx 函数是你手写的运行时；css 走 setAttribute；vino 是固定约定名。

05

你猜对了，我的 jsx 是直接注册的 window.jsx = (tag: string | Function, props?: any, ...childs: any[]) => { ... }，然后下边是我对 brk 的类型定义：

type FunctionComponent<Props> = (props: Props) => HTMLElement;

interface BasicProps {
	cls?: string;
	css?: string;
	clk?: Function;
}

interface brk {
	// 一个全局且统一的卡片组件
	card: FunctionComponent<BasicProps>;
	// 显示一个SVG图标
	icon: FunctionComponent<{ d: string; c?: string; styles?: object }>;

	/** 打开一个任意的目标 */
	opens: (meta: any) => any;

	// 网络请求相关的工具
	_json: (path: string) => Promise<object>;
	_post: (path: string, body: object) => Promise<object>;
	_edit: (path: string, body: object) => Promise<object>;

	// 加载一个异步组件，type=module
	_load: (src: string) => Promise<any>;
	// opens a regular link
	_open: (key: string, target?: string) => any;

	// global shared caches
	v: any;

	// 一个弱引用，key = html dom 实例
	weak: WeakMap;
}

归档。window.jsx 全局注册；brk 命名空间包含 card / icon / opens / _load / _open / _json / _post / _edit / v / weak。

两个疑问：brk.opens(meta) 里的 meta 是什么形状？icon 用 styles: object 是有意区分还是历史遗留？

06

你猜对了，我确实没有虚拟 DOM，而是直接根据状态变化重新生成新 DOM；降低复杂度，严格保证了 UI = f(state)，而不像 React 那样内部 hooks 乱飞，组件逻辑不断重复执行；

icon 用 styles 先不管，后边我会补充，主要是因为 svg 底层走的是 document.createElementNS 所以不太一样；

brk.opens 是重点，不同的环境实现不一样，但目前的功能定义是打开新页面；

现在我给你介绍一下架构设计，也就是我的初始网页结构是，首先一个 html 携带一个 /static/init.css 及 /static/init.js 初始化模板，将 window.jsx 和 window.brk 两个全局变量准备好；文件非常小，只有不到 10kb；所以我的这个库最重要的特征之一是轻量化；

然后紧接着 <script>brk.render({"load":"/dist/project/module/page.mjs"})</script> 这段配置是服务器 Server Side Render 生成的；

对于网页环境，brk.render = (meta) => brk._load(meta.load).then(v => { document.body.appendChild( v.page.vino({}) ) })

归档。没有虚拟 DOM，直出真实 DOM；init.js 一次性注入 window.jsx 和 globalThis._brk_；这是 server-driven bootstrap。

一个疑问：既然没有 vdom，状态变化后"重建的粒度"怎么界定？

07

你说的对，我确实是 server-driven bootstrap；其次，最核心的问题，没错，前端组件最重要的永远是状态；

我这个库对提供的解决方案，就是不解决！让用户自己去 div.replaceChildren() 和 div.textContent 去更新 dom 和任何内容。

也就是说，我这个库，核心的是，只提供整体架构的语法糖，所以做到了体积这么小，但可扩展性强，我有很多扩展的功能和界面组件库。

针对你的问题，最简单的组件就是这样子：

const PlayGround = () => {
	const ref = {
		counter: 0,
	};

	const placeholder = (
		<div>
			<div>点击了 {ref.counter++} 次</div>
		</div>
	);

	const clicked = () => {
		placeholder.replaceChildren((
			<div>点击了 {ref.counter++} 次</div>
		));
	};

	return (
		<div>
			<div>其他静态内容</div>
			{placeholder}
			<button clk={clicked}>按钮</button>
		</div>
	);
};

核心定位记下了：brk 不解决状态管理，只提供语法糖。

注意两个隐含约定：DOM 节点可直接作为 children；"锚点 + replaceChildren"是官方更新姿势。

问：这种锚点模式是推荐裸写，还是会提供辅助 API？

08

你知道我的 import {brk} from '@/brk'; 这行代码里做了什么吗？除了由 TypeScript 来给 IDE 的类型提示，其实本质只有一行代码：

export const brk = globalThis._brk_ || {};

因此我的架构逻辑很简单，由提前编译好的独立的 /static/init.js 初始化模板，去初始化微前端的执行环境，主要就是 jsx 和 brk 变量啦，然后每个页面都以 esm/module 的格式 export const page = { vino } 这样每个页面编译出来的代码几乎全部 100% 是应用代码，基本无关框架的代码了。

归档。@/brk 是类型壳，运行时真身是 globalThis._brk_。页面产物几乎没有框架代码。

两个问题：@/ 是 esbuild alias 还是 TS paths？同一个页面被打开两次时，vino 会重新执行还是复用？

09

你讲到的是多页面问题，我的解决办法依然是不解决：由用户开发一个自定义的父页面（每个项目自定义一种页面挂载风格），这个页面留有 placeholder 用于挂在附带的子页面：

const MultiplePagesApp = () => {
	const pages = [{ name: '菜单页面一', load: '/dist/project/module/page1.mjs' }, ...];

	const body = (
		<div css="flex: 1; min-height: 80vh"/>
	);

	brk.opens = (page) => brk._load(page.load).then(v => {
		body.replaceChildren((
			<v.page.vino/>
		));
	});

	return (
		<div>
			<header><h1>统一的应用部分</h1></header>
			<main css="display: flex">
				<menu css="min-width: 240px;">
					{pages.map(it => (
						<div clk={() => brk.opens(it)}>
							{it.name}
						</div>
					))}
				</menu>
				{body}
			</main>
			<tail>© Hello World</tail>
		</div>
	);
};

归档。brk 不做应用组装，只做应用组装的语法糖。

注意 <v.page.vino/> 这种多级成员标签是运行时动态取组件。

问：<v.page.vino/> 是 esbuild 原生支持的吗？子页面 DOM 被丢弃后 weak 数据消失，是设计预期吗？

10

1. 是的，初始化模板中的 brk.opens = ()=>{} 是一个不会报错的空函数。

2. 肯定是支持的，组件返回数组（jsx() 内部有对应的 flatten 处理，甚至可以数组套数组）、<a.b.c.d/> 组件、设置 <data.list[0]/> 组件都支持，只有 <div/> 这种全小写字母且没有小数点（动态取子对象引用）才会被 document.createElement(tag) 渲染成原生的 HTMLElement，这些都是 esbuild 本身就支持的。

3. brk.weak 是特意设计的，因为 dom 会被主动挂载，消失是随着不受控的垃圾回收机制，这个控制不了，因此，如果 dom 存在就可以去尝试获取相关联的内部状态和组件方法，这个涉及到了又一个重点问题 —— 父组件如何调用子组件。

React 的思路是将回调函数设置为 props 传递给子组件，然后实时同步子组件的状态，还有用各种 ref 去传递方法，并且看起来是不鼓励调用子组件的方法，各种写法看起来好麻烦；

我的思路依旧是交给用户去处理，可以用 brk.weak.set(dom, {state, handlers})，也可以用：

const ctx: any = {}; // 把所有权交给子组件，去赋值

const test = () => {
    // 在父组件里调用子组件的方法，和状态
    ctx.action_from_child(ctx.state_from_child);
}

return(
    <div> <DemoChild ctx={ctx}/> </div>
)

归档。brk.opens 默认空函数是设计而非偷懒；标签解析规则完全交给 esbuild；ctx 是双向交接——父创建空对象，子往里挂状态和方法。

问：ctx 的有效期怎么界定？ctx 和 brk.weak 是二选一还是可以并用？

11

我的重点是渲染一个组件永远只执行一次（ctx 对象的生命周期肯定是跟随父组件的，父组件没了子组件也就没了，子组件的销毁与重建是由父组件严格控制的），即生成一次 DOM 结构，内部的局部更新由这个组件自己去负责。

可以的，拉个目录吧，也不知道你听懂了没有，反正很琐碎，而且这还只是我这个框架的骨架。后边还有与 WebComponent 生态的互动等很多技术细节，框架主要提供思想和简单示例，以及自身融合最少的代码（永远小于 10kb），后期可以扩展，即通过 brk._load / 即 import() 去加载动态功能，然后挂载在 brk 上，供所有的页面去复用功能，达到同样功能只引入一次的目标。

听懂了——brk 不做调度，组件只渲染一次，一切由用户显式掌控。
